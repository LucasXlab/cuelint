# 选题：CueLint（字幕体检）

调查日期：2026-10-29。所有外部链接均为当日可打开的公开页面。GitHub 数据通过 GitHub API 读取；issue 数量、评论数是读取时的快照。没有引用无法打开的帖子，也没有把功能请求改写成用户原话。

## 0. 结论

做 **CueLint**：一个本地运行的字幕质检与修复命令行工具。它把 Whisper、剪映、YouTube 自动字幕、翻译工具产出的 SRT/VTT，在发布前按明确规则检查并修到可读：每行长度、每秒字数、行数、最小时长、重叠、重复、空字幕，以及词表一致性。输出修好的字幕和一份可复查的 HTML 报告。不联网、不上传视频、不需要账号。

一句话用户：**每周用自动字幕或翻译字幕做口播视频，发布前还要逐条拖动时间轴改错字的独立创作者和课程制作者。**

选择理由不是“字幕是热点”，而是：现有工具要么是大型 GUI（Subtitle Edit），要么只负责转写（WhisperX），要么只做时间轴同步（ffsubsync）；中间“发布前的可读性质检 + 批处理 + 可进 CI”这一层是空的。这个流程每周都会发生，30 秒能演示出前后差异，而且核心算法可以在一版里做透。

## 3. 四个通过门槛的候选：最强两个竞品

方法：每个竞品读 README、读取最近 100 条 issue（按评论数倒序；少于 100 条的全读）、挑出评论最多的负反馈。GitHub 没有星级评分，这里的“最差评价”指公开 issue 中负面且讨论最多的记录，不是编造的评分。数据日期 2026-10-29。

### 3.1 CueLint

没有直接竞品。最强的两个替代方案是 Subtitle Edit（编辑/批处理 GUI）和 WhisperX（字幕上游的转写/对齐）。这不是“竞品做得差”，而是它们的目标不同，留下了质检层。

**Subtitle Edit**（14,775 stars，MIT，C#/.NET）
- README：跨平台桌面 GUI，Windows 10 22H2 起；macOS 12+；Linux 走 Flatpak。没有 CLI 用法或“检查规则文件”的说明。
- 最近 issue 里负反馈：整季批量提取内嵌字幕无反应（#6342）；用户要“Netflix Timing Fixer”自动按规范修（#4697）；过短字幕要手动分两步延长（#4892）；大量控件无无障碍标注（#12087）。
- 没做好的 3 件事：
  1. **不可脚本化。** 只有 GUI 和批处理对话框，没有“规则文件 + 退出码 + 机器可读报告”，无法放进渲染流水线或 CI。
  2. **可读性规则不是一等公民。** 行长、CPS、行数、最小时长散落在多个工具/功能里，不能一次按一个 profile 检查并解释每条为什么不合格。
  3. **批量失败不可诊断。** #6342 这类问题表现为“没反应”，没有逐文件的结果清单，用户不知道哪一集失败、为什么失败。

**WhisperX**（24,931 stars，BSD-2-Clause，Python）
- README：需要 Python、ffmpeg，GPU 加速要 CUDA 12.8；卖点是词级时间戳和说话人分离，不是字幕可读性。
- 最近 issue 里负反馈：时间戳偏 10–15 秒（#810）；强制对齐从 3.3.3 起不准（#1220）；一个段出现 4 行以上（#1145）；加长度限制后断句破坏可读性（#829）。
- 没做好的 3 件事：
  1. **上游只对时间戳负责。** 它输出的是转写段，不是发布级字幕；行长、CPS、两行限制都要下游自己做。
  2. **错误发现得太晚。** 时间戳漂移和错误断句要在播放器里逐条看才发现，缺一个发布前的硬门槛。
  3. **安装重。** CUDA、模型、ffmpeg 对只想修 SRT 的人是过重的依赖；质检层应该零模型、零 GPU。

### 3.2 多账户持仓合并与真实收益

**Ghostfolio**（9,607 stars，AGPL-3.0，TypeScript）
- README：自建需要 PostgreSQL + Redis，官方推荐付费云服务；PWA；面向多平台、买入持有。
- 最近 issue 负反馈：CSV 导入手工资产错配/重复创建（#5193）；净收益率显示错误（#5793）；不存在的外币却报缺汇率（#2558）；克隆活动又新建资产（#5324）。
- 没做好的 3 件事：
  1. **导入的数据完整性没有硬门槛。** 错配、重复资产能直接写进库，用户看到的是“收益率错了”而不是“第 37 行映射错了”。
  2. **计算口径不可复核。** 收益率异常时只有结果，没有逐笔现金流和计算口径可以对照。
  3. **自建太重。** PostgreSQL、Redis、缓存、升级迁移，对一个只想每月对账的人不划算。

**Portfolio Performance**（4,129 stars，EPL-1.0，Java）
- README：桌面应用，Eclipse RCP；导入靠 PDF/CSV importer；文档以德语社区为主。
- 最近 issue 负反馈：账户多次转移后 FIFO 错误（#4446）；追加买入后 TTWROR 不对（#615）；只能 FIFO、不能按券商用移动平均（#4503）；手机优先券商导入要手动倒文件（#5863）。
- 没做好的 3 件事：
  1. **导入仍是桌面时代的假设。** 对账单在手机里时，必须先倒到电脑；移动优先券商用户被排除。
  2. **成本口径不跟随券商。** FIFO/移动平均不能按账户选，和券商对不上账。
  3. **学习成本高。** 概念多、菜单深，第一次用的人很难在 30 分钟内得到“我的真实收益是多少”。

### 3.3 交易日志与逐笔复盘

**TradeNote**（979 stars，GPL-3.0，JavaScript）
- README：隐私、简单、灵活；Docker Compose 自带 MongoDB；面向日交易者。
- 最近 issue 负反馈：部分买卖不识别（#139）；IBKR symbol 为空（#78）；同一天不能多账户/多券商导入（#71）；只支持 USD 交易对（#38）；没有手工录入（#107）；日历错误（#50）。
- 没做好的 3 件事：
  1. **导入正确性没有对账步骤。** 部分成交、列名映射、非 USD 对都直接导致错账，用户只能事后发现。
  2. **多账户/多券商是后补的。** 同一天只能导入一次、账户维度缺失，和真实交易者的账户结构不匹配。
  3. **运行依赖重。** MongoDB + Node + Docker，为记几十笔交易维护一套数据库不划算。

**Trade Journal（LuxAlgo）**（549 stars，MIT，TypeScript）
- README：SQLite、本地优先、broker sync、AI reflection；明确标注“Early release”，API 和 schema 可能变；各导入格式的验证程度不一致。
- 最近 issue 负反馈：去重哈希合并真实成交（#52）；多账户复制交易被合并（#10）；多币种直接相加（#31）；期货/期权 ROI 忽略乘数（#34）。
- 没做好的 3 件事：
  1. **成交身份不稳定。** 去重不包含账户和券商执行 id，真实成交会被静默合并。
  2. **多币种/多资产类别没打通。** 混合币种直接相加，期货乘数漏算，统计结果不可信。
  3. **早期版本缺兼容承诺。** README 自己写明 schema 会变，导入格式验证程度不一，用户不敢长期存数据。

### 3.4 订阅续费雷达

**Wallos**（8,762 stars，GPL-3.0，PHP）
- README：自托管 Web 应用，Docker 部署，多币种、通知、OIDC。
- 最近 issue 负反馈：SMTP 配置失败（#17、#520）；ntfy 通知不工作（#524、#826）；时区导致提醒晚一天（#777）；家庭共享没有归属（#709）；iCal 缺失（#496）。
- 没做好的 3 件事：
  1. **提醒送达没有验收。** 配置界面能填，但邮件/推送失败原因埋在 PHP 异常里，用户不知道提醒到底会不会来。
  2. **时间与时区不是一等公民。** 容器时区、显示时区、通知时区混在一起，续费提醒晚一天就失去意义。
  3. **共享订阅没有模型。** 家庭场景只能建共享账号，费用归属和分摊都靠人记。

**Subscription Management**（899 stars，MIT，TypeScript）
- README：本地 SQLite、多币种、报表、Docker、深色主题。
- 全部 36 条 issue 已读；负反馈：Docker 启动失败（#5、#10）；结束日期提醒缺失（#13）；年付没有折算月成本（#16）；首次使用要配 API key（#21）；没有一键 docker run（#30）。
- 没做好的 3 件事：
  1. **首次使用门槛高。** 要配 API key、要改 compose，装完还不能直接用。
  2. **统计口径误导。** 首页显示“本月支出”，年付订阅不折算，用户看不到真实月成本。
  3. **通知能力弱。** 缺结束日期提醒和送达验证，续费场景最关键的“提前知道”没有做透。

## 4. 打分

每项 1–5 分。只有通过证据门槛的 4 个候选参与打分。

| 候选 | 痛点证据强度 | 我每周会用 | 30 秒演示价值 | 竞品空间 | 一个核心流程第一版做透 | 总分 |
|---|---:|---:|---:|---:|---:|---:|
| **CueLint 字幕体检** | 4 | 5 | 5 | 4 | 5 | **23** |
| 多账户持仓合并 | 5 | 5 | 4 | 2 | 3 | 19 |
| 交易日志与复盘 | 5 | 4 | 4 | 3 | 3 | 19 |
| 订阅续费雷达 | 4 | 3 | 4 | 2 | 4 | 17 |

打分理由：
- CueLint 的痛点证据不如持仓/交易日志“金额算错”那么刺眼（4 分），但字幕问题每条视频都会出现，且现有工具没有把“规则 + 修复 + 报告”合起来；核心流程只依赖 SRT 文本，第一版能做完，不依赖券商文件或 OAuth，所以“做透”是 5。
- 持仓合并和交易日志的痛点更强（5 分），但都受制于券商格式、账户模型、税务口径，第一版很难既准确又通用；竞品已经很多且强，空间只有 2–3 分。
- 订阅工具的证据真实，但用户每月才打开一次，竞品 Wallos 已经覆盖大部分需求，差异化只剩“提醒可靠”，空间 2 分。

## 5. 选定：CueLint

### 5.1 第一版只做这一条核心流程

```bash
cuelint fix episode-07.srt --profile bilibili-zh --report report.html
```

1. 读入 SRT/VTT，解析失败时指出行号和原因，不写出半成品。
2. 按 profile 检查：每秒字数、每行宽度、行数、最小时长、最大时长、重叠、重复、空字幕。
3. 能安全修的自动修：断行、拆段、去重、清空、修重叠、补最小时长；不能安全修的（文本缺失、时间无法分配）保留原样并列出。
4. 输出 `episode-07.fixed.srt` 和 `report.html`；终端给出“修复前 18 个问题 / 修复后 2 个 / 2 个需要人工”。
5. `check` 不写文件，只报告；`--fail-on error` 时有问题返回非 0，可直接进 CI。

### 5.2 适用于

- 用 Whisper、剪映、YouTube 自动字幕做口播/课程视频，发布前要统一字幕规范的人。
- 一次要处理多集、多个语言版本，需要批处理和同一套阈值的人。
- 用 Remotion、ffmpeg 或自建流水线做程序化视频，想把“字幕不合格”挡在渲染之前的人。

### 5.3 不适用于

- 需要听打、翻译、语音转文字：CueLint 不处理音频，只处理已有字幕文件。
- 需要把字幕强制对齐到音频：时间轴同步请用 ffsubsync/AutoSubSync；CueLint 只做可读性和一致性检查。
- 需要 ASS 特效、图形字幕、卡拉 OK 逐字变色：这些是排版/渲染工具的工作，第一版只处理 SRT 和 WebVTT。

### 5.4 选它要接受的代价

- 受众比“个人理财”小，但需求更具体，演示更直接。
- 规则阈值必须能解释、能配置，否则会变成“另一个主观的自动修改器”；第一版所有默认值都要有出处，修复动作必须可回退（保留原文件，只写新文件）。
- 不做音频意味着无法验证“字幕是否真的对得上声音”；这是刻意的边界，README 要写清楚。
